# ADR-0007：正文改用「内置字码本 + 8 MB 块 zstd」

> 取代 [ADR-0003](0003-block-compressed-content.md) 的**压缩算法与块大小**两节；
> ADR-0003 关于「为什么不按章压缩」「为什么不转 GB18030」「为什么不选 brotli / lzma」的判断仍然成立。

- 状态：已采纳
- 日期：2026-11-01
- 相关迁移：`0017_codebook_blocks.sql`

## 背景

ADR-0003 定的是 1 MB 块 + zstd-best，当时口径 838 本 / 4.87 GB 正文、34.7%。
生产库已经长到 **20,110 本 / 7,911,456 章 / 79,488,303,333 字节原始正文 / 87,626 块**，
库内正文 BLOB 27,561,086,682 字节 = **34.67%**，正文占库体积 95%。

[compression-research](compression-research.md) 的结论：UTF-8 的 3 字节/字里有大量结构性冗余
（每字前 3 位固定、续字节高 2 位固定），zstd 吃不到；先按字频重编码再压，全库 200 本实测 26.8%，
贴着 1 阶上下文的理论下限 26.3%。

## 决定

1. 新增块格式 **0x03 = zstd( 码本流 )**，成为唯一写入格式；`0x00`/`0x01`/`0x02` 读路径永久保留。
2. **码表编进二进制**（`go:embed`），版本化、默认启用、零配置——不引入外部字典文件，也不需要用户做任何设置。
3. 块目标大小 **1 MB → 8 MB**。

## 为什么码本是主力（NAS 200 本实测，往返全部通过）

| 方案 | 压缩率 | 单块解压 P50 | P95 |
|---|---|---|---|
| 现状：1 MB 块纯 zstd | 33.42% | 1.4 ms | 1.8 ms |
| 码本 + 1 MB 块 | 28.08% | 4.3 ms | 4.8 ms |
| **码本 + 8 MB 块** | **26.45%** | **32.5 ms** | **37.6 ms** |
| 码本 + 整本 | 25.98% | 34.3 ms | 169 ms |
| 纯整本 zstd（对照） | 30.05% | 11.2 ms | 65 ms |

码本单独贡献 **5.3 个百分点**，压缩还更快（码流更短，zstd 吞吐 16.2 → 20.7 MB/s）。

## 为什么是 8 MB 而不是整本

**整本相对 8 MB 块只省 0.47 个百分点，却把 P95 从 37.6 ms 拉到 169 ms、内存拉到 15 倍。**

- 最大的一本书（book_id 30423，10,434 章 / 75,066,493 字节）整本解压稳态 **310 ms**、HeapAlloc 峰值 **386 MB**、进程 RSS 峰值 **1.43 GB**；
  NAS 只有 7 GB 内存，并发送几本就撑爆；8 MB 块下同一本书单章读取 33 ms、常驻内存约 26 MB。
- 整本在 16–40 MB 档就已经 P50 90 ms、>40 MB 档 211 ms；8 MB 块全程稳定在 32–38 ms。
- 8 MB 块仍然保留「块内跨章节匹配」这个收益来源——ADR-0003 说的「1 MB 是拐点」，在码本把数据压到 46% 之后，
  拐点后移到 8 MB：再往上加窗口，zstd 已经吃不到新东西了。

## 码本布局（v1，改布局即升版本号）

| 首字节 | 含义 | 容量 |
|---|---|---|
| `0x00`–`0xBF` | 字频前 192 字，1 字节 | 192 |
| `0xC0`–`0xDF` + 次字节 | 2 字节码 | 8,192 |
| `0xE0`–`0xFE` | 三字节层直接等于码点，解码不查表 | 全部合法码点 |
| `0xFF` | 转义段：长度 + 原始字节 | 非法 UTF-8 字节 |

- 三字节层等于码点，所以**任何字符都不会比 UTF-8 更差**：长尾生僻字 3→3 字节，4 字节 emoji 4→3。
- 192 是拐点：前 192 覆盖 63.185%，前 8,384 覆盖 99.993%；再往 1 字节层塞会让长尾从 2 退化到 3 字节，是净亏。
- 全库加权 **1.368 字节/字**（UTF-8 的 45.6%），真实正文实测 1.3647。

## 码表怎么来的

扫全库 `chapter_blocks` 解压还原后按 rune 统计（`tests/tools/corpusstats`，只读）：
**26,957,660,602 个字符 / 35,912 个不同字符 / 20 个非法字节**（全是 0xAC）。
`Train(字频).MarshalBinary()` → `internal/textcode/codebook_v1.bin`（8,384 项 / 33,556 字节）。

码表自描述：魔数 `NVTC` + 版本 + 布局 + 项数 + 码点 + CRC32C，版本 / 布局 / CRC 任一不符即拒载。

## 别人拿什么接入

`internal/textcode` 是**叶子包，只依赖标准库**：

```go
raw, _ := textcode.Encode(nil, utf8Bytes)   // UTF-8 → 码本流
back, _ := textcode.Decode(nil, raw)        // 码本流 → UTF-8，逐字节相同
textcode.Version()                          // 码表版本
```

换用自己的语料：`corpusstats` 统计字频 → `textcode.Train(freq)` → `MarshalBinary()` → 替换 `codebook_v1.bin`。
对比不同方案：`cmd/codebench`（`-db -sample -out`）。

## 后果

### 正面
- 正文 27.56 GB → 约 21–22.7 GB（抽样 26.45% / 加权外推 28.52%），全库省 4.9–6.5 GB。
- 压缩速度反而更快（16.2 → 20.7 MB/s），迁移不再比现在更慢。
- 容器零额外依赖，码表随二进制走，不需要运维放字典文件。

### 代价
- 翻页单块解压 1.4 ms → 32.5 ms（P95 37.6 ms）。阅读页连续翻页需要调用方自持块缓存。
- 8 MB 块覆盖的章节数变多，一块损坏的影响面从约 35 章扩大到约 280 章。
- 码表是「全库字频」的快照：新导入的书带来新字符时走三字节兜底，不报错、不丢字，只是这部分不走 1/2 字节层。
  码表重建需要全库重压。
