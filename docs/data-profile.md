# 语料画像（实测）：样本目录 4.4GB / 865 个中文 txt

> 所有数字来自对源目录的实测扫描（2026-10-24），不是估计。目的是把「解析器要面对什么」写清楚，
> 并为验收时的抽样指标提供基线。

## 1. 规模

| 指标 | 数值 |
|---|---|
| 目录总大小 | 4.1 GiB（`du -sh`）/ 4.43 GB（字节合计） |
| txt 文件数 | 865 |
| 其它文件 | `.DS_Store`、一个 `.pdf`、一个扩展名被拼坏的文件（`631.【示例短篇】.txt-----------------------`） |
| 单文件体积 | 最小 ~0，中位 4.33 MB，p95 12.57 MB，最大 42.21 MB |
| 大于 20 MB | 6 个 |
| 小于 50 KB | 1 个 |
| 子目录 | 存在 `待处理/` 等子目录，扫描必须递归 |

## 2. 编码分布（全量 300KB 头部探测 + 整文件复核）

| 探测结果 | 文件数 | 说明 |
|---|---|---|
| UTF-8 BOM | 215 | 带 \xEF\xBB\xBF，必须先剥 BOM 再解析 |
| GB18030（GBK 超集） | 261 | 传统网文站主流编码 |
| UTF-8 无 BOM | 72 | — |
| UTF-16（带 BOM） | 4 | 含 \x00 字节，按行分割会全乱 |
| 「头部探测失败」 | 313 | **不是坏文件**：前 300 KB 探测失败，但整文件按 GB18030 解码成功 |

**结论（对解析器的硬要求）**

1. 不能只嗅探文件头：**必须支持整文件重试与分段自适应**（候选集：utf-8 / utf-8-sig / gb18030 / utf-16le / utf-16be / big5）。
2. 判定用「CJK 字符命中率 − U+FFFD 替换字符惩罚」打分选最优，而不是「第一个解码不报错的编码」。
3. 部分文件是**混合编码**（不同章节来自不同抓取源），单编码解码会局部乱码；v1 允许残留少量 U+FFFD，但要求行级可读。

## 3. 章节标题格式分布（60 个随机文件的「主导模式」）

| 主导模式 | 文件数 |
|---|---|
| `第N章` | 46 |
| 序章 / 楔子 / 引子 / 尾声 / 番外 等 | 4 |
| `第N节` / `第N回` | 3 |
| `第N卷` / `第N部` / `第N集` | 3 |
| 纯数字行（`0001`、`1、`） | 2 |
| 中文数字条目（`一、xxx`） | 1 |
| 无任何章节标记（短篇/肉文） | 若干 |

**在同一文件内**常见组合（必须支持混合）：`第N卷` 作分组 + `第N章` 作章；`正文 第N章` 带前缀；
`第01章`、`第1章`、`第一章` 混用；标题后可能紧跟广告行；一章内还可能嵌 `（1）` 之类子标题。

## 4. 噪声模式（几乎每本书都有）

```
示例书源群 A：
免费资源一群：100000001 / 免费资源二群：100000002 / 中转一群：100000003
【本作品来自互联网及出版图书，如侵犯作者合法权益，可私下联系处理……】
==========================
您下载的该文件来自；示例书吧   欢迎访问 http://www.example.com
example-site.com@ / [示例书源] / TXT000000
==================== 分 隔 线 ====================
```

清洗策略：**只在章节边界与正文首尾做保守清洗**，段中出现的疑似广告行仅在「行长 < 60 且命中噪声词典」时删除，避免误删正文。

## 5. 文件名携带的元数据

文件名是元数据的第一来源，形态极不规整：

| 形态 | 示例 |
|---|---|
| 序号 + 书名 + 章节范围 | `10.1长夜书简（1-1990）.txt` |
| 编号 + 编号 + 书名 | `918.1556.示例三字书名.txt` |
| 书名号包裹 + 作者 | `《示例书名》全集(Zei8.com).txt` |
| 标签前缀 + 书名 + 状态 + 作者 | `☆文笔好10%△《山居杂记（七改）》.txt` |
| 作者内嵌 | `《城南旧事》…… 作者：示例作者A.txt` |
| 站点前缀 | `example-site.com@《小镇旧闻》……[示例书源][示例书源].txt` |

**结论**：书名/作者抽取必须是「文件名规则优先 → 正文头部元信息块 → 文件名清洗兜底」三级回退，
且要剥掉 `☆…10%☆`、`[示例书源]`、`TXT000000`、`example-site.com@` 这类装饰。

## 6. 特殊结构

- **单文件多书合集**：如 `695.1333.《多人合集示例》作者：多人.txt`（13 MB，内含多部作品）。按章号重置点自动拆成多本（每段 ≥3 章），第 N 段来源路径标 `#N`。
- **章节极多**：单本 6000+ 章（`865.1503.『示例长篇』（0001-6177）`），目录必须可虚拟滚动。
- **章节极短 / 无标记**：短篇几百 KB 无章节行，需要兜底切分（整篇单章或按 8000 字等分）。

## 7. 验收基线（导入完成后必须检查）

```sql
-- 1) 上架数量：应接近 865（允许因幂等/重复内容少量减少）
SELECT count(*) FROM books;
-- 2) 章节总数：经验值 30 万 ~ 80 万量级
SELECT sum(chapter_count), sum(word_count) FROM books;
-- 3) 异常书：章节数 < 2 或 0（说明切分失败）
SELECT id, title, chapter_count FROM books WHERE chapter_count < 2 ORDER BY chapter_count LIMIT 50;
-- 4) 空章节（正文为空）
SELECT count(*) FROM chapters WHERE length(trim(content)) = 0;
-- 5) 编码分布
SELECT encoding, count(*) FROM books GROUP BY encoding;
-- 6) 单章超长（> 3 万字，说明漏切）
SELECT book_id, id, length(content) FROM chapters WHERE length(content) > 90000 ORDER BY 3 DESC LIMIT 20;
-- 7) FTS 完整性
INSERT INTO chapters_fts(chapters_fts) VALUES('integrity-check');
```

## 8. 全文检索选型实测（256 MB 中文语料）

| 方案 | 库体积 | 插入耗时 | 3 字查询 | 2 字查询 |
|---|---|---|---|---|
| 无 FTS 索引 | 1.00x | 1.1 s | — | — |
| FTS5 `trigram` | **2.96x** | 91 s | 0.3 ms / 109 命中 | **0 命中（不支持 <3 字）** |
| FTS5 `unicode61` + 汉字逐字加空格（`content_seg` 列） | **1.76x** | 15 s | 0.3 ms / 109 命中（查询侧同样分段） | 0.3 ms / 5 命中 |

**采用字级分词方案**：体积小 40%、构建快 6 倍，且支持 2 字检索；代价是查询串也要过同一个分段函数
（`store.Segment`），且 1 字查询无意义（接口层直接拒绝）。

> 本节是**当时的选型记录**。该方案在全量库里占掉 65% 的体积，已按 [ADR-0002](adr/0002-drop-fulltext-index.md) 移除；
> 容量结论见 §10。

### 9.7 驾驶舱性能修复（已收敛，2026-10-25）

**修复前**在真实规模下是秒级到分钟级，根因是几处全表扫描：

| SQL | 修复前耗时 | 原因 |
|---|---|---|
| （旧形态）`SUM(length(content)+length(title_seg)+length(content_seg))` on `chapters` | **99~1024 s** | 逐行读 4.2 GB 正文 + 分词镜像列 |
| （旧形态）`SUM(length(block))` on `chapters_fts_data` | **20~48 s** | 逐行读 FTS 影子表（3.2 GB） |
| 把 `chapters.word_count` 全表拉进 Go 逐行分桶 | **73.6 s** | 读整行记录（含正文） |
| `dbstat` 虚表全库扫描 | **74.9 s** | 逐页读，不可用 |

关键实测对照（同库同机器）：

| 操作 | 耗时 | 结论 |
|---|---|---|
| `COUNT(*) FROM chapters` | 0.11 s | 只读 btree，可用 |
| `SUM(word_count) FROM chapters` | 0.05 s | 整数列，可用 |
| `SUM(length(content)) FROM chapters` | 54 s | 文本列要读整行，慢 1000 倍 |
| 区间 `COUNT` 走 `idx_chapters_wc` 覆盖索引 | 0.01~0.09 s | 采用 |

**修复方案（预计算 + 覆盖索引）**：

1. **`store_metrics` 表**（迁移 0004）：键位 `text_bytes` / `book_text_bytes` /
   `chapter_word_sum` / `index_bytes` / `metrics_version` / `refreshed_at_unix`。
   正文字节在导入时顺手累加（导入本来就要遍历所有章节，零额外成本），
   与章节写入同一事务，不会漂移。读接口只查表。
2. **`idx_chapters_wc` 覆盖索引**：章节长度分桶改成「一条 SQL 里 N 个区间 `COUNT`」，
   每个子查询走覆盖索引做区间 SEARCH，只读 `word_count` 一列。
   最初试过 `CASE WHEN + GROUP BY`，要走整条索引 0.09 s，比区间 SEARCH 慢约 9 倍。
3. **容错**：缓存缺失或 `metrics_version` 落后时，接口照常 200，但把
   `compositionEstimated` / `stale` 标为 `true`；服务启动时后台异步补算一次，算完自动转正常。

**实测结果（838 本 / 422,715 章 / 13.8 GiB，HTTP 端到端各 10 次）**：

| 接口 | P50 | P95 | max | 目标 | 判定 |
|---|---|---|---|---|---|
| `GET /api/stats` | 1.12 ms | 1.31 ms | 1.44 ms | < 100 ms | ✅ |
| `GET /api/health/report` | 26.34 ms | 28.48 ms | 29.04 ms | < 100 ms | ✅ |

**数值准确性**：预计算值与全表精确值逐项完全一致（误差 0）：

```
text_bytes       metrics=4729622979   精确=4729622979   ✅
book_text_bytes  metrics=174104       精确=174104       ✅
chapter_word_sum metrics=1411582902   精确=1411582902   ✅
```

导入时 `store_metrics` 同步累加，导入后差值与新书完全吻合（+274 字符 / +30 字）；
`Force` 覆盖写入不会重复计数（有测试守着）。

**新增字段**（只加不改，前端可忽略）：`Stats.compositionEstimated`、`HealthReport.stale`。

**运维入口**：`store.RefreshMetrics(ctx)` 可全表精确重算（13.8 GiB 库实测 75 s）。

## 10. 容量推算：几十万到百万本

> 目标问题：**同一套 SQLite 库（0018 起两个文件：主库 + 正文库），从 7.1 万本扩到
> 30 万 / 50 万 / 100 万本，还能不能扛？**
> 数字来自生产库实测锚点（71,320 本 / 24,697,647 章 / 主库 2.8 GB / 正文库 61.8 GB）
> 加本机 100 万本合成库实跑（§10.3），不含任何真实书名/作者/路径。
>
> 口径：**每本 346.3 章**（生产库实测 24,697,647 / 71,320）。旧文档的「每本 504 章」
> 来自 838 本早期样本，已被全量生产库推翻——它把章节总数高估了 46%。

### 10.1 每本口径：书是元数据，章才是体积

拆库之后「每本多少 MB」不再是有意义的单位，两个文件的增长轴不同：

| 文件 | 随什么增长 | 生产库实测 | 每章摊薄 |
|---|---|---|---|
| **主库**（元数据 + 章节行 + 索引） | 书目 + **章节行数** | 2.8 GB | 122 字节/章 |
| **正文库**（`chapter_blocks` 压缩块） | 只有正文 | 61.8 GB | 2.62 KB/章 |
| **合计** | — | **64.6 GB** | **2.74 KB/章** |

主库 2.8 GB 里只有约 0.5 GB 是书目本身（100 万本实测见 §10.3），其余是 2,469 万条
章节行与三个二级索引。**「书多」不贵，「章多」才贵。**

### 10.2 体积推算：30 万 / 50 万 / 100 万本

| 书数 | 章节数 | 主库 | 正文库 | **合计** | 单盘判定 |
|---|---|---|---|---|---|
| 71,320 | 2,469 万 | 2.8 GB | 61.8 GB | **64.6 GB** | 生产现状（实测） |
| 300,000 | 1.04 亿 | 11.8 GB | 260 GB | **272 GB** | 可行（需 ≥ 400 GB 可用） |
| 500,000 | 1.73 亿 | 19.6 GB | 433 GB | **453 GB** | 临界（需 ≥ 700 GB 可用） |
| 1,000,000 | **3.46 亿** | **39.3 GB** | **867 GB** | **906 GB** | 需 ≥ 1.4 TB 或拆盘 |

推导：两列都是「生产库每章摊薄 × 目标章数」，目标章数 = 目标书数 × 346.3。
**正文库是唯一体积瓶颈**，占合计 96%；主库到 100 万本也只有 39 GB。

> `/api/stats` 的三分项（`text_bytes` 61.8 / `index_bytes` 1.15 / `other_bytes` 2.9 GB）
> 是同一批数据的另一种切法，**不要与上表两列重复相加**。前者按「压缩块 / btree / 余量」分，
> 后者按「主库文件 / 正文库文件」分；三分项之和 65.85 GB 略大于文件合计 64.6 GB 属正常，
> `fillComposition` 会按比例归一到文件合计。

### 10.3 延迟实测：100 万本合成库

```bash
python3 scripts/bench-capacity.py --books 1000000 --chapters 346 \
    --sample-books 86000 --samples 20
```

实跑：**100 万行书目 + 33.3 万行作者 + 2,975.6 万行章节，主库 2.6 GB，建库 132 s**。
下表 P50 单位 ms（超 1 s 写成秒）。「轴」列说明外推依据，见 §10.5 末。

| 操作 | 形态 | 实测 P50 | 轴 | **推算 @ 3.46 亿章** | 判定 |
|---|---|---|---|---|---|
| 书架分页（word_count DESC, LIMIT 20） | — | 10.0 | 书 | 10.0 ms | 可用 |
| 书名 LIKE 子串（`%…%` 全表） | — | 47 | 书 | 47 ms | 可用 |
| **书名 + 作者 LIKE（JOIN authors）** | — | **1.13 s** | 书 | **1.13 s** | **临界** |
| 单本目录（346 章，ORDER BY idx） | — | 0.16 | 固定 | 0.16 ms | 可用 |
| 随机读一章元数据（按主键） | — | 0.01 | 固定 | 0.01 ms | 可用 |
| 章节总数 `COUNT(*) FROM chapters` | 旧 | 84 | 章 | 978 ms | 应移除 |
| 章节总数 读 `store_metrics.chapter_count` | 新 | 0.01 | 固定 | 0.01 ms | 可用 |
| 长度直方图 `CASE WHEN` + GROUP BY | 旧 | **5.50 s** | 章 | **64.0 s** | **不可用** |
| 长度直方图 区间 COUNT 走 `idx_chapters_wc` | 中间 | 651 | 章 | **7.57 s** | **不可用** |
| 长度直方图 读 `chapter_length_hist` | 新 | 0.01 | 固定 | 0.01 ms | 可用 |
| import-trend `chapters JOIN books` | 旧 | 1.02 s | 章 | **11.9 s** | **不可用** |
| import-trend `books` 归集 SUM(chapter_count) | 中间 | 32 | 书 | 32 ms | 可用 |
| import-trend 读 `import_daily` | 新 | 0.11 | 固定 | 0.11 ms | 可用 |
| 章节字数总和 `SUM(word_count)` | 旧 | 803 | 章 | **9.35 s** | **不可用** |
| 章节字数总和 读 `store_metrics` | 新 | 0.01 | 固定 | 0.01 ms | 可用 |
| authors 聚合 LEFT JOIN UNION + GROUP BY | 旧 | **2.42 s** | 书 | **2.42 s** | **临界** |
| authors Top50 读 `author_agg` | 新 | 59 | 固定 | 59 ms | 可用 |

三层形态的含义（每行标明所属层，不要混着读）：

- **旧 = 请求路径上的全表聚合**，0022 之前的原始形态；
- **中间 = 0022 之前的最优解**（区间 COUNT 走覆盖索引、只扫 books 归集），
  常数压下去了但**增长率没变**，百万本时依然不可用；
- **新 = 0022 的预计算表**（`chapter_length_hist` / `import_daily` / `author_agg` /
  `store_metrics.chapter_count`），写入时增量维护，读路径只查表，**与行数无关**。

「新」层是读真实预计算表跑出来的（建库时按业务表回填，与 `refresh-metrics` 同口径），
不是按「固定」轴假设出来的。

### 10.4 结论：100 万本可以扛，但要满足三个前提

**前提：① 0022 已应用（聚合走预计算表）② 正文库有 900 GB 以上单独空间
③ 不把作者/书名子串检索当成高频路径。**

能扛的部分：

1. **交互路径完全不随总量增长**：读单章 0.01 ms、取目录 0.16 ms、书架分页 10.0 ms，
   走主键或 B-tree SEARCH，100 万本与 7 万本是同一量级。
2. **驾驶舱聚合全部降到毫秒级**：四组查询在 2,975.6 万章实测 **0.01 ~ 59 ms**
   （`store_metrics` / `chapter_length_hist` / `import_daily` 都是 0.01~0.11 ms；
   `author_agg` 59 ms，因为要 JOIN 回 `authors` 取名字），且**不再随章节数增长**——
   这是 0022 的全部意义，也是 100 万本与 3 万本的区别所在。
3. **主库不是问题**：100 万本 39.3 GB，比正文库小一个数量级，备份/VACUUM 都不难。

要认账的部分：

1. **正文库 867 GB 是唯一硬约束**：单盘要 1.4 TB 可用才舒服（VACUUM 还要一份等效空间）。
   拆盘或分库必须提前规划。
2. **书名 + 作者 LIKE 在 100 万本时 1.13 s**：现状是 `%关键词%` 子串匹配，
   **没有索引帮得上忙**（前导通配符让 B-tree 失效），只能全表扫 books 再 JOIN authors；
   300 万本会到 3.5 s 量级。**这是已知且真实的扩展风险**，且无法靠预计算解决——
   输入是用户任意关键词。要做高频检索得引入倒排/前缀索引或外部检索引擎。
3. **authors 聚合旧形态 2.42 s**：UNION 两分支各扫一遍再全量 GROUP BY，300 万本约 7.3 s。
   它被 `author_agg` 解决了，但旧路径仍保留作降级——**降级路径在百万本时不可用**：
   预计算表缺失时接口不 500，但会慢到超时。这是有意的取舍。
4. **写是单写者**：WAL 一写多读，百万本批量导入仍须按批串行；且每次章节写入都要
   同事务维护三张预计算表，导入吞吐低于 0022 之前（代价换到写入侧，是有意的）。
5. **冷启动首批请求偏慢**：§9.7 记录过 2,500 万章 `COUNT(*)` 冷缓存首查 7.3 s。别用热态数字算 SLA。

### 10.4.1 驾驶舱查询全部预计算化（0022）

上一节说「聚合不在请求路径上」在**生产规模下并不完全成立**：真实库长到 7 万本 / 2,469 万章后，
还有四个驾驶舱接口在请求路径上扫全表。迁移 0022 把它们全部改成读预计算表。

**实测基线**（NAS 生产库 71,320 本 / 24,697,647 章 / 主库 2.8 GB / 正文库 61.8 GB）：

| 接口 | 改造前 | 根因 |
|---|---|---|
| `GET /api/stats/import-trend?days=14` | **28.85 s** | `chapters JOIN books` 按日归集，2,469 万行拉进 Go 逐行 `parseTime` |
| `GET /api/health/report` | **3.35 s**（9 请求并发 25.5 s） | 章节长度直方图 5 段区间 `COUNT`，每段扫全部 `idx_chapters_wc` 索引项 |
| `GET /api/stats` | 152 ms | 每次请求 `COUNT(*) FROM chapters` |
| `GET /api/authors?sort=words` | 319 ms（并发 1.4 s） | `authors LEFT JOIN (UNION) LEFT JOIN books GROUP BY` 全表聚合 |

**改造后**（本机合成库 71,320 本 × 346 章 = 24,676,720 章，与生产同量级；各 6 次取 P50）：

| 操作 | 改造前 | 改造后 | 倍数 |
|---|---|---|---|
| `Stats`（含 `COUNT(*) FROM chapters`） | 169 ms | **18 ms** | 9.4x |
| `HealthReport`（含长度直方图） | 1950 ms | **36 ms** | 54x |
| `ImportTrend(14)` | 15973 ms | **0.03 ms** | 500000x |
| `ListAuthors(sort=words)` | 255 ms | **15 ms** | 17x |
| `ListAuthors(sort=books)` | 257 ms | **15 ms** | 17x |

**做法**：三张预计算表 + 一个既有键，全部在写入路径同事务增量维护，迁移时回填一次。

| SQL（改造前） | SQL（改造后） |
|---|---|
| `SELECT b.imported_at FROM chapters c JOIN books b ON b.id=c.book_id WHERE b.imported_at >= ?` | `SELECT day, book_count, chapter_count FROM import_daily` |
| `SELECT (COUNT(*) …) FROM chapters WHERE word_count >= ? AND < ?`（×5 段） | `SELECT bucket, count FROM chapter_length_hist` |
| `SELECT COUNT(*) FROM chapters` | `SELECT value FROM store_metrics WHERE key='chapter_count'` |
| `authors LEFT JOIN (SELECT … UNION SELECT …) LEFT JOIN books GROUP BY a.id` | `authors a JOIN author_agg g ON g.author_id=a.id ORDER BY g.word_count DESC LIMIT ?` |

**三条不变量**（都有测试守着，见 `internal/store/dashboard_precompute_test.go`）：

1. **增量 == 全量**：走完导入/覆盖/追更/改正文/删章/插入/拆章/合章/删书之后，
   增量维护出的三张表与「清空后按全表重算」逐项相等；
2. **缓存 == 实时**：预计算路径与原实时 SQL 给出同一张趋势表、同一页作者、同一组直方图；
3. **缺失不 500**：预计算表缺失/未回填/口径版本落后/时区偏移变化时，读接口降级为实时算
   并标 `stale`（`/api/stats` 用 `compositionEstimated`），接口照常 200。

**运维**：迁移自带回填；`norvels refresh-metrics` 会重算三张表与 `store_metrics`。
回填期间读接口返回 stale 而不是报错，算完自动转正常。

> 口径注意：`import_daily.day` 是**本地日**（与 §9.7 的 `countByDay` 同口径：`parseTime → t.Local()`），
> 库里的 `imported_at` 是 UTC 文本；直接把 UTC 文本截前 10 位会把北京时间凌晨导入的书算到前一天。
> 时区偏移随回填一起记进 `store_metrics.precompute_zone_offset`，偏移一变即判过期。

### 10.5 复现方式

```bash
make bench-capacity                                    # 500 本 x 500 章，几秒

# 100 万本口径：元数据全量 + 前 8.6 万本建章节（约 3 GB 库，建库 2 min + 测量 6 min）
python3 scripts/bench-capacity.py --books 1000000 --chapters 346 \
    --sample-books 86000 --samples 20

python3 scripts/bench-capacity.py --books 1000000 --chapters 0   # 仅元数据，509 MB

# 线性度自证：章节翻倍则章节轴查询同步翻倍（实测 COUNT 85→167 ms、区间 COUNT 652→1310 ms）
python3 scripts/bench-capacity.py --books 1000000 --chapters 346 --sample-books 172000
```

**为什么可以只给前 8.6 万本书建章节**：两条正交的外推轴，各自单独验证。

- **元数据轴不抽样**：books / authors / books_authors 全量真建 100 万行。书架分页、
  书名检索、authors 聚合只扫这几张表，与 chapters 无关；要给百万本下结论就必须有
  百万行真实 B-tree。
- **章节轴按需缩减**：章节侧 SQL 全是对 `chapters` 的一次顺序扫描（COUNT / SUM /
  5 段区间 COUNT / 旧形态 JOIN），代价与行数严格线性——没有随机 I/O、没有排序。
  实测 30M → 60M 章时 `COUNT(*)` 85 → 167 ms、区间 COUNT 652 → 1310 ms，比值 1.96 / 2.01，
  在线性区内，可按比例外推到 3.46 亿章。
- **例外已单列**：按主键读、按 `book_id` 取目录、LIMIT 分页标「固定」轴，系数取 1。

脚本默认在系统临时目录建库、跑完自删（`--keep` 保留），markdown 直接输出到 stdout；
建库前按 `df` 检查余量，不够即 exit 2 并打印需要的 GB 数。

### 压缩口径（12 本 / 53.2 MB 真实语料，Go 真实跑）

**关键发现：按章独立压缩吃不到跨章的重复词。** 章节平均只有 13 KB 左右，压缩器在这么短的
窗口里攒不出足够的重复模式；改成按块压缩后体积几乎减半——同一个 zstd-best，按章 49%，
按 1 MB 块只要 34.1%。所以**压缩单位比压缩算法本身更关键**。

| 方案 | 256 KB 块 | 1 MB 块 | 4 MB 块 | 1 MB 块解压 P50 |
|---|---|---|---|---|
| `zstd-best` | 37.3% | **34.1%** | 31.9% | **0.99 ms** |
| `brotli-9` | 36.0% | 33.0% | 31.0% | 4.37 ms |
| 按章独立 `flate-6` | — | 49.0% | — | 0.015 ms |

**采用 zstd-best + 1 MB 块**，三条理由：

1. **不选整本压缩**：4 MB 块 31.9%，只比 1 MB 块好 2.2 个百分点，但读一章要解压整本
   （十几 ms、内存峰值几十 MB），读放大不划算。
2. **不选 brotli**：只多压 1.1 个百分点（33.0% vs 34.1%），解压却慢 4.4 倍（4.37 ms vs 0.99 ms）。
3. **1 MB 是拐点**：256 KB → 1 MB 收益 3.2 个百分点，1 MB → 4 MB 只剩 2.2，再往上递减。

上表是 12 本样本的预估。**真实库实测更权威**：838 本 / 422,715 章跑完整迁移后，
正文压成 5,130 个块共 **1.69 GB**（原始 4.87 GB，压缩率 **34.7%**），逐章 SHA-256 校验全部一致；
VACUUM 后全库 **1.62 GB**。所以 10.2 的「压缩后」列用实测值，不用 34.1% 的外推。

> 早前记录的「flate-6 49% / zstd 51%」是**按章独立压缩**的旧口径，已被上表取代——
> 那组数字没错，但压缩单位选错了，不该拿它算全库容量。
