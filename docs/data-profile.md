# 语料画像（实测）：样本目录 4.4GB / 865 个中文 txt

> 所有数字来自对源目录的实测扫描（2026-10-24），不是估计。目的是把「解析器要面对什么」写清楚，
> 并为验收时的抽样指标提供基线。

## 1. 规模

| 指标 | 数值 |
|---|---|
| 目录总大小 | 4.1 GiB（`du -sh`）/ 4.43 GB（字节合计） |
| txt 文件数 | 865 |
| 其它文件 | `.DS_Store`、一个 `.pdf`、一个扩展名被拼坏的文件（`631.【示例短篇】.txt-----------------------`） |
| 单文件体积 | 最小 ~0，中位 4.33 MB，p95 12.57 MB，最大 42.21 MB |
| 大于 20 MB | 6 个 |
| 小于 50 KB | 1 个 |
| 子目录 | 存在 `待处理/` 等子目录，扫描必须递归 |

## 2. 编码分布（全量 300KB 头部探测 + 整文件复核）

| 探测结果 | 文件数 | 说明 |
|---|---|---|
| UTF-8 BOM | 215 | 带 \xEF\xBB\xBF，必须先剥 BOM 再解析 |
| GB18030（GBK 超集） | 261 | 传统网文站主流编码 |
| UTF-8 无 BOM | 72 | — |
| UTF-16（带 BOM） | 4 | 含 \x00 字节，按行分割会全乱 |
| 「头部探测失败」 | 313 | **不是坏文件**：前 300 KB 探测失败，但整文件按 GB18030 解码成功 |

**结论（对解析器的硬要求）**

1. 不能只嗅探文件头：**必须支持整文件重试与分段自适应**（候选集：utf-8 / utf-8-sig / gb18030 / utf-16le / utf-16be / big5）。
2. 判定用「CJK 字符命中率 − U+FFFD 替换字符惩罚」打分选最优，而不是「第一个解码不报错的编码」。
3. 部分文件是**混合编码**（不同章节来自不同抓取源），单编码解码会局部乱码；v1 允许残留少量 U+FFFD，但要求行级可读。

## 3. 章节标题格式分布（60 个随机文件的「主导模式」）

| 主导模式 | 文件数 |
|---|---|
| `第N章` | 46 |
| 序章 / 楔子 / 引子 / 尾声 / 番外 等 | 4 |
| `第N节` / `第N回` | 3 |
| `第N卷` / `第N部` / `第N集` | 3 |
| 纯数字行（`0001`、`1、`） | 2 |
| 中文数字条目（`一、xxx`） | 1 |
| 无任何章节标记（短篇/肉文） | 若干 |

**在同一文件内**常见组合（必须支持混合）：`第N卷` 作分组 + `第N章` 作章；`正文 第N章` 带前缀；
`第01章`、`第1章`、`第一章` 混用；标题后可能紧跟广告行；一章内还可能嵌 `（1）` 之类子标题。

## 4. 噪声模式（几乎每本书都有）

```
示例书源群 A：
免费资源一群：100000001 / 免费资源二群：100000002 / 中转一群：100000003
【本作品来自互联网及出版图书，如侵犯作者合法权益，可私下联系处理……】
==========================
您下载的该文件来自；示例书吧   欢迎访问 http://www.example.com
example-site.com@ / [示例书源] / TXT000000
==================== 分 隔 线 ====================
```

清洗策略：**只在章节边界与正文首尾做保守清洗**，段中出现的疑似广告行仅在「行长 < 60 且命中噪声词典」时删除，避免误删正文。

## 5. 文件名携带的元数据

文件名是元数据的第一来源，形态极不规整：

| 形态 | 示例 |
|---|---|
| 序号 + 书名 + 章节范围 | `10.1长夜书简（1-1990）.txt` |
| 编号 + 编号 + 书名 | `918.1556.示例三字书名.txt` |
| 书名号包裹 + 作者 | `《示例书名》全集(Zei8.com).txt` |
| 标签前缀 + 书名 + 状态 + 作者 | `☆文笔好10%△《山居杂记（七改）》.txt` |
| 作者内嵌 | `《城南旧事》…… 作者：示例作者A.txt` |
| 站点前缀 | `example-site.com@《小镇旧闻》……[示例书源][示例书源].txt` |

**结论**：书名/作者抽取必须是「文件名规则优先 → 正文头部元信息块 → 文件名清洗兜底」三级回退，
且要剥掉 `☆…10%☆`、`[示例书源]`、`TXT000000`、`example-site.com@` 这类装饰。

## 6. 特殊结构

- **单文件多书合集**：如 `695.1333.《多人合集示例》作者：多人.txt`（13 MB，内含多部作品）。v1 只标记 `MultiBook=true`，不自动拆分。
- **章节极多**：单本 6000+ 章（`865.1503.『示例长篇』（0001-6177）`），目录必须可虚拟滚动。
- **章节极短 / 无标记**：短篇几百 KB 无章节行，需要兜底切分（整篇单章或按 8000 字等分）。

## 7. 验收基线（导入完成后必须检查）

```sql
-- 1) 上架数量：应接近 865（允许因幂等/重复内容少量减少）
SELECT count(*) FROM books;
-- 2) 章节总数：经验值 30 万 ~ 80 万量级
SELECT sum(chapter_count), sum(word_count) FROM books;
-- 3) 异常书：章节数 < 2 或 0（说明切分失败）
SELECT id, title, chapter_count FROM books WHERE chapter_count < 2 ORDER BY chapter_count LIMIT 50;
-- 4) 空章节（正文为空）
SELECT count(*) FROM chapters WHERE length(trim(content)) = 0;
-- 5) 编码分布
SELECT encoding, count(*) FROM books GROUP BY encoding;
-- 6) 单章超长（> 3 万字，说明漏切）
SELECT book_id, id, length(content) FROM chapters WHERE length(content) > 90000 ORDER BY 3 DESC LIMIT 20;
-- 7) FTS 完整性
INSERT INTO chapters_fts(chapters_fts) VALUES('integrity-check');
```

## 8. 全文检索选型实测（256 MB 中文语料）

| 方案 | 库体积 | 插入耗时 | 3 字查询 | 2 字查询 |
|---|---|---|---|---|
| 无 FTS 索引 | 1.00x | 1.1 s | — | — |
| FTS5 `trigram` | **2.96x** | 91 s | 0.3 ms / 109 命中 | **0 命中（不支持 <3 字）** |
| FTS5 `unicode61` + 汉字逐字加空格（`content_seg` 列） | **1.76x** | 15 s | 0.3 ms / 109 命中（查询侧同样分段） | 0.3 ms / 5 命中 |

**采用字级分词方案**：体积小 40%、构建快 6 倍，且支持 2 字检索；代价是查询串也要过同一个分段函数
（`store.Segment`），且 1 字查询无意义（接口层直接拒绝）。

> 本节是**当时的选型记录**。该方案在全量库里占掉 65% 的体积，已按 [ADR-0002](adr/0002-drop-fulltext-index.md) 移除；
> 容量结论见 §10。

### 9.7 驾驶舱性能修复（已收敛，2026-10-25）

**修复前**在真实规模下是秒级到分钟级，根因是几处全表扫描：

| SQL | 修复前耗时 | 原因 |
|---|---|---|
| `SUM(length(content)+length(title_seg)+length(content_seg))` on `chapters` | **99~1024 s** | 逐行读 4.2 GB 正文 + 分词镜像列 |
| `SUM(length(block))` on `chapters_fts_data` | **20~48 s** | 逐行读 FTS 影子表（3.2 GB） |
| 把 `chapters.word_count` 全表拉进 Go 逐行分桶 | **73.6 s** | 读整行记录（含正文） |
| `dbstat` 虚表全库扫描 | **74.9 s** | 逐页读，不可用 |

关键实测对照（同库同机器）：

| 操作 | 耗时 | 结论 |
|---|---|---|
| `COUNT(*) FROM chapters` | 0.11 s | 只读 btree，可用 |
| `SUM(word_count) FROM chapters` | 0.05 s | 整数列，可用 |
| `SUM(length(content)) FROM chapters` | 54 s | 文本列要读整行，慢 1000 倍 |
| 区间 `COUNT` 走 `idx_chapters_wc` 覆盖索引 | 0.01~0.09 s | 采用 |

**修复方案（预计算 + 覆盖索引）**：

1. **`store_metrics` 表**（迁移 0004）：键位 `text_bytes` / `book_text_bytes` /
   `chapter_word_sum` / `index_bytes` / `metrics_version` / `refreshed_at_unix`。
   正文字节在导入时顺手累加（导入本来就要遍历所有章节，零额外成本），
   与章节写入同一事务，不会漂移。读接口只查表。
2. **`idx_chapters_wc` 覆盖索引**：章节长度分桶改成「一条 SQL 里 N 个区间 `COUNT`」，
   每个子查询走覆盖索引做区间 SEARCH，只读 `word_count` 一列。
   最初试过 `CASE WHEN + GROUP BY`，要走整条索引 0.09 s，比区间 SEARCH 慢约 9 倍。
3. **容错**：缓存缺失或 `metrics_version` 落后时，接口照常 200，但把
   `compositionEstimated` / `stale` 标为 `true`；服务启动时后台异步补算一次，算完自动转正常。

**实测结果（838 本 / 422,715 章 / 13.8 GiB，HTTP 端到端各 10 次）**：

| 接口 | P50 | P95 | max | 目标 | 判定 |
|---|---|---|---|---|---|
| `GET /api/stats` | 1.12 ms | 1.31 ms | 1.44 ms | < 100 ms | ✅ |
| `GET /api/health/report` | 26.34 ms | 28.48 ms | 29.04 ms | < 100 ms | ✅ |

**数值准确性**：预计算值与全表精确值逐项完全一致（误差 0）：

```
text_bytes       metrics=4729622979   精确=4729622979   ✅
book_text_bytes  metrics=174104       精确=174104       ✅
chapter_word_sum metrics=1411582902   精确=1411582902   ✅
```

导入时 `store_metrics` 同步累加，导入后差值与新书完全吻合（+274 字符 / +30 字）；
`Force` 覆盖写入不会重复计数（有测试守着）。

**新增字段**（只加不改，前端可忽略）：`Stats.compositionEstimated`、`HealthReport.stale`。

**运维入口**：`store.RefreshMetrics(ctx)` 可全表精确重算（13.8 GiB 库实测 75 s）。

## 10. 容量推算：几万本

> 目标问题：**同一个单文件 SQLite 库，从 838 本扩到 3 万 ~ 5 万本，还能不能扛？**
> 本节把第 8、9 节的实测基线外推成容量结论，并把「哪些操作会退化」写清楚。
> 所有基线都来自真实库与本机合成库实测，不含任何真实书名/作者/路径。

### 10.1 实测基线（三个规模）

| 规模 | 书/章 | 库体积 | 来源 |
|---|---|---|---|
| 真实全量库 | 838 本 / 422,715 章 | **14.84 GB**（正文 4.87 GB + 分词镜像 6.28 GB + FTS 3.30 GB） | §9 全量导入实测 |
| 合成库（压测） | 5,000 本 x 5,000 章 = 2,500 万章 | **15.5 GB** | 本机压测 |
| 合成库（压测） | 50,000 本（仅元数据） | 数十 MB | 本机压测 |

真实库体积构成：**65% 花在正文索引上**（分词镜像 6.28 GB + FTS 影子表 3.30 GB = 9.58 GB / 14.84 GB），
真正的原文只有 4.87 GB。这是第 8 节选型的直接代价，也是 §10.2 三列对照的由来。

### 10.2 体积推算：838 / 3,000 / 10,000 / 30,000 / 50,000 本

**每本口径**（真实库 838 本实测均值，线性外推；每本平均 504 章）：

| 口径 | 每本平均 | 相对原文 | 说明 |
|---|---|---|---|
| 原文 | 5.29 MB | 1.00x | 源 txt 平均体积 |
| 现状（含分词镜像 + FTS） | 17.71 MB | 3.35x | 14.84 GB / 838 |
| 砍掉正文索引后 | 约 6.3 MB | 1.19x | 正文 B-tree + 书名/作者/目录索引 + 其他 |
| 再压缩正文后 | **1.93 MB** | **0.36x** | 真实库实测：VACUUM 后 1.62 GB / 838 本 |

推导：砍索引后 6.3 MB = 5.29 MB x 1.19（页内碎片、`books`/`authors` 行、各列索引）。

压缩后这一列**是实测值，不是外推**：生产库副本（13.83 GB / 838 本 / 422,715 章）跑完迁移
+ VACUUM 后实测 **1.62 GB**。其中正文压成 5,130 个块共 **1.69 GB**（原始 4.87 GB，压缩率 **34.7%**），
VACUUM 回收空洞页后落到 1.62 GB。

**总容量对照**（章节数按每本 504 章估算）：

| 书数 | 章节数 | 现状（含分词镜像 + FTS） | 砍掉正文索引后 | 再压缩正文后 |
|---|---|---|---|---|
| 838 | 42.3 万 | **14.8 GB** | **5.3 GB** | **1.62 GB**（实测） |
| 3,000 | 151 万 | 53 GB | 19 GB | 5.8 GB |
| 10,000 | 504 万 | 177 GB | 63 GB | 19 GB |
| 30,000 | 1,513 万 | 531 GB | 189 GB | 58 GB |
| 50,000 | 2,522 万 | 885 GB | 315 GB | 97 GB |

读法：

- **现状形态撑不到几万本**：5 万本要 885 GB，其中约 570 GB 是可省的正文索引；
- **砍掉正文索引后**，5 万本 315 GB，已经落回单盘可承受区间；
- **再压缩正文**，5 万本 97 GB，与 838 本原始语料（4.4 GB）相比只涨 22 倍，而不是 200 倍。

> 838 那一行是**真实库实测**（迁移 + VACUUM 后 1.62 GB），其余规模按每本 1.93 MB 线性外推。
> 外推假设「每本章节数与压缩率不变」，实际会随语料差异略有浮动。

### 10.3 延迟推算：哪些操作会退化到亚秒级

合成库实测（2,500 万章）+ 真实库实测（42 万章），按行数线性外推：

| 操作 | 42 万章（实测） | 504 万章（推算） | 1,513 万章（推算） | 2,522 万章（推算） | 2,500 万章（实测） | 判定 |
|---|---|---|---|---|---|---|
| `COUNT(*) FROM chapters` | 0.018 ~ 0.11 s | 21 ms | 62 ms | 103 ms | 102 ms（首查 max 7.3 s） | 亚秒级，随行数线性 |
| `SUM(word_count)` | 0.05 s | 146 ms | 438 ms | 729 ms | 723 ms | 亚秒级，且已预计算进 `store_metrics` |
| 区间 N 段计数（覆盖索引） | 0.01 ~ 0.09 s | 118 ms | 354 ms | 589 ms | 584 ms | 亚秒级，随行数线性 |
| 单本目录查询（5,000 章） | 0.31 ms | 2.45 ms | 2.45 ms | 2.45 ms | 2.45 ms（max 11.25 ms） | **毫秒级，与总行数无关** |
| 随机读一章正文 | P50 0.32 ms | 0.01 ~ 0.32 ms | 同左 | 同左 | P50 0.01 ms / max 0.09 ms | **毫秒级，按主键 SEARCH** |
| 随机读一章正文（**压缩后实测**） | P50 0.08 ms / P95 1.35 ms | 同左（按块解压，与总行数无关） | 同左 | 同左 | — | **毫秒级，解压 1 个块** |
| 书名 `LIKE` 全表（838 行） | 0.41 ms | — | — | — | 5 万行 18.4 ms | 毫秒级 |
| 书架分页 | — | — | — | — | 5 万本 0.02 ~ 2.5 ms | 毫秒级 |
| 书名 + 作者 `LIKE`（5 万本） | — | — | — | — | 18.4 ms | 毫秒级 |

**两档泾渭分明**：

1. **毫秒级（不随总量增长）**：按主键取单章、按 `(book_id, idx)` 取整本目录、书架分页、书名/作者 `LIKE`。
   这些走 B-tree SEARCH 或覆盖索引，几万本与 838 本的耗时是同一个量级——
   2,500 万章时单本目录仍是 2.45 ms，读单章正文 P50 0.01 ms；
   压缩存储后读单章 P50 0.08 ms（多一次块解压），仍与总行数无关。**交互路径不受容量影响。**
2. **亚秒级（随行数线性增长）**：全表 `COUNT`、`SUM(word_count)`、区间分桶统计。
   2,500 万章时落在 100 ~ 730 ms；5,000 万章量级会到 1.5 s 附近。
   **这类操作的前提是「不要放进请求路径」**——而本项目恰恰没放（见 10.4）。

还要注意**首查抖动**：2,500 万章的 `COUNT(*)` 冷缓存首查实测 7.3 s，热了才 102 ms。
page cache 上限 64 MB 相对几十 GB 的库可以忽略，真正兜住热路径的是操作系统页缓存，
所以服务刚启动后的第一批请求要按「冷」预期，别拿热态数字做 SLA。

### 10.4 结论：几万本可以扛

**结论：3 万 ~ 5 万本在单文件 SQLite 上可行，前提是正文索引已移除、仪表盘走预计算。**

三条支撑：

1. **体积**：砍掉正文索引后每本约 6.3 MB，5 万本 315 GB；再压缩正文后每本 **1.93 MB**（真实库实测 1.62 GB / 838 本），5 万本 **97 GB**。
   现状形态（每本 17.71 MB）的 885 GB 才是真正的天花板，而这块体积 65% 是正文索引。
2. **延迟**：交互路径（读单章、取目录、书架分页、书名检索）始终是毫秒级，与总行数无关；
   会随行数增长的只有全表聚合（`COUNT`/`SUM`/区间统计），2,500 万章实测最坏 0.73 s。
3. **聚合不在请求路径上**：仪表盘用的 `text_bytes` / `chapter_word_sum` 等值在导入时同事务预计算
   进 `store_metrics`（§9.7），读接口只查表（`/api/stats` P95 1.31 ms），
   **所以全表 `SUM` 不会落在请求路径上**；章节长度分布走 `idx_chapters_wc` 覆盖索引区间 SEARCH，
   也比全索引扫描快约一个数量级。

仍然要认账的边界（都在离线/运维侧，不在交互侧）：

- **备份与迁移是整文件复制**：97 GB 的单文件备份一次要按小时计，`VACUUM` 还需要额外一份等效空间；
- **写是单写者**：WAL 允许一写多读，几万本的批量导入仍应按批串行，不要并发写同一库；
- **冷启动第一批请求偏慢**：见 10.3 的首查抖动；
- **压缩后的读放大**：每读一章要先解压它所在的块，真实库实测 **P50 0.08 ms / P95 1.35 ms**，
  目录查询（4,413 章的书）1.93 ms；仍远快于一次磁盘随机读，交互无感。

### 10.5 复现方式

```bash
# 小规模（500 本 x 500 章，约 1 GB 临时库，几秒跑完；不碰 data/norvels.db）
make bench-capacity

# 大库压测必须显式传参；脚本会先查磁盘余量，不够直接拒绝并打印需要的 GB 数
python3 scripts/bench-capacity.py --books 5000 --chapters 5000

# 只测元数据（几万本书只占几十 MB）
python3 scripts/bench-capacity.py --books 50000 --chapters 0
```

脚本默认在系统临时目录建库、跑完自动删除（`--keep` 保留），输出可直接贴进本文的 markdown 表格。
默认不建 FTS 正文索引（`--fts on` 可复现现状形态），对应 10.2 里「砍掉正文索引后」那一列。

### 压缩口径（12 本 / 53.2 MB 真实语料，Go 真实跑）

**关键发现：按章独立压缩吃不到跨章的重复词。** 章节平均只有 13 KB 左右，压缩器在这么短的
窗口里攒不出足够的重复模式；改成按块压缩后体积几乎减半——同一个 zstd-best，按章 49%，
按 1 MB 块只要 34.1%。所以**压缩单位比压缩算法本身更关键**。

| 方案 | 256 KB 块 | 1 MB 块 | 4 MB 块 | 1 MB 块解压 P50 |
|---|---|---|---|---|
| `zstd-best` | 37.3% | **34.1%** | 31.9% | **0.99 ms** |
| `brotli-9` | 36.0% | 33.0% | 31.0% | 4.37 ms |
| 按章独立 `flate-6` | — | 49.0% | — | 0.015 ms |

**采用 zstd-best + 1 MB 块**，三条理由：

1. **不选整本压缩**：4 MB 块 31.9%，只比 1 MB 块好 2.2 个百分点，但读一章要解压整本
   （十几 ms、内存峰值几十 MB），读放大不划算。
2. **不选 brotli**：只多压 1.1 个百分点（33.0% vs 34.1%），解压却慢 4.4 倍（4.37 ms vs 0.99 ms）。
3. **1 MB 是拐点**：256 KB → 1 MB 收益 3.2 个百分点，1 MB → 4 MB 只剩 2.2，再往上递减。

上表是 12 本样本的预估。**真实库实测更权威**：838 本 / 422,715 章跑完整迁移后，
正文压成 5,130 个块共 **1.69 GB**（原始 4.87 GB，压缩率 **34.7%**），逐章 SHA-256 校验全部一致；
VACUUM 后全库 **1.62 GB**。所以 10.2 的「压缩后」列用实测值，不用 34.1% 的外推。

> 早前记录的「flate-6 49% / zstd 51%」是**按章独立压缩**的旧口径，已被上表取代——
> 那组数字没错，但压缩单位选错了，不该拿它算全库容量。
